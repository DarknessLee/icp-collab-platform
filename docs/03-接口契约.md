# 03 · 接口契约（M1 冻结）

> 冻结规则：M1 验收通过后本文件冻结；M2 如需变更接口，先改本文 + `docs/04`，再改代码，变更记入 DECISIONS。
> 权威来源：本文件与 `docs/04-数据模型与种子.md`；前后端不一致时以本文件为准。

## 1. 全局规范

### 1.1 基础

| 项 | 约定 |
| --- | --- |
| Base Path | `/api/v1` |
| 风格 | RESTful；资源名复数（`/users`、`/policies`）；动作型接口用子路径（`/policies/{id}/publish`、`/tasks/{id}/approve`） |
| 编码 | UTF-8；`Content-Type: application/json; charset=UTF-8` |
| 时间 | 请求/响应统一 `yyyy-MM-dd HH:mm:ss`（日期字段 `yyyy-MM-dd`）；后端本地时区 +08:00 |
| ID | 统一字符串或数字均可，前端按字符串处理（防精度丢失）；本文示例用字符串 |
| 金额 | 字符串或数字均可，前端按字符串展示两位小数；接口层统一 `BigDecimal` → JSON number（保留 2 位） |
| 枚举出参 | `{code, label}` 双字段（如 `{"code":2,"label":"已生效"}`）；入参用 `code` 数字 |
| 命名 | JSON 字段 camelCase；路径 kebab-case 或单词小写 |

### 1.2 统一返回

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "traceId": "8f3c2a1b9d4e4f6a"
}
```

- `code=0` 成功；非 0 失败（前端按错误码处理，`message` 仅提示）。
- HTTP 状态码：业务失败也返回 200，仅鉴权/框架级异常用 401/403/404/500（前端同时兼容 body.code）。
- 所有响应头带 `X-Trace-Id`，与 `traceId` 一致。

### 1.3 分页

请求：`pageNum`（默认 1）、`pageSize`（默认 10，最大 100）。
响应 `data`：

```json
{ "list": [], "total": 0, "pageNum": 1, "pageSize": 10 }
```

列表通用查询参数：`keyword`（模糊匹配主名称/编码）、`status`、`deptId`、`startDate`、`endDate`、`orderBy`（白名单字段）、`orderDir`（asc/desc）。各接口只声明特有的额外参数。

### 1.4 鉴权

- 登录后 `Authorization: Bearer <accessToken>`；access 2h、refresh 7d。
- 未登录/token 过期：`40100`；token 非法/被篡改：`40103`；刷新用 `POST /auth/refresh`。
- 权限：接口级 `@PreAuthorize("hasAuthority('system:user:list')")`，权限标识即 `sys_menu.perms`；无权限 `40300`。
- 数据权限：服务层统一 `DataScopeInterceptor`（本人/本部门/本部门及下级/全部），越权访问 `40300`（不返回他人数据，返回空列表或 404 均可，统一 403 便于验收）。
- CORS：允许源由 `app.cors.allowed-origins` 配置（逗号分隔，默认 `http://localhost:5173`、`http://127.0.0.1:5173`、`http://localhost:4173`、`http://127.0.0.1:4173`）；允许方法 `GET/POST/PUT/DELETE/PATCH/OPTIONS`、允许全部请求头、暴露 `X-Trace-Id`、`allowCredentials=true`、预检缓存 3600s。

### 1.5 错误码

| code | 含义 | HTTP |
| --- | --- | --- |
| 0 | 成功 | 200 |
| 40000 | 参数校验失败（message 给首个字段错误） | 200 |
| 40001 | 业务状态不允许（如已完成的单据重复审批） | 200 |
| 40002 | 重复提交/幂等冲突 | 200 |
| 40100 | 未登录或登录过期 | 401 |
| 40101 | 用户名或密码错误（不区分账号不存在） | 200 |
| 40102 | 账号已锁定 | 200 |
| 40103 | token 非法/过期 | 401 |
| 40300 | 无权限（功能权限或数据权限） | 403 |
| 40400 | 资源不存在 | 200 |
| 41300 | 文件过大/类型不允许 | 200 |
| 42900 | 操作过于频繁 | 200 |
| 50000 | 系统异常（message 通用文案，详情看 traceId 日志） | 500 |

### 1.6 幂等与并发

- 关键写接口（流程发起、审批、整改复核、评价计划审批、采购/用印提交）要求请求头 `Idempotency-Key`（UUID），后端 5 分钟内同 key 返回首次结果。
- 列表/详情类 GET 幂等；PUT 全量更新、PATCH 局部更新（Demo 统一用 PUT）。
- 乐观并发：单据类更新带 `version` 字段（M2 引入，本文预留）。

### 1.7 文件与导出

| 接口 | 说明 |
| --- | --- |
| `POST /files` | multipart `file`，返回 `{id,originalName,size,suffix,contentType}`；白名单 pdf/png/jpg/jpeg/doc/docx/xls/xlsx/zip，≤20MB |
| `GET /files/{id}/download` | 权限校验后流式下载，文件名 Content-Disposition |
| `GET /files/{id}/preview` | 图片/PDF 内联预览（其他类型 41301 不支持） |
| `GET /{module}/export` | 导出 Excel（同步返回 xlsx 流），权限与列表一致 |

### 1.8 实时消息

`GET /messages/stream?access_token=<JWT>`（SSE，`text/event-stream`）：事件 `message`，data 为 `{id,type,title,content,createTime}`；EventSource 不能带自定义 header，鉴权用 query `access_token`（服务端校验并脱敏日志，无/坏 token 401）；心跳 30s；单用户最多 3 连接，超限关闭最旧；断线由前端指数退避重连（见 §6.1 第 8 条）。

```json
  "expiresIn": 7200,
  "user": { "id": "2", "username": "icpadmin", "realName": "林晓", "deptId": "2", "deptName": "内控合规部" },

```

菜单约定（M1 实测冻结）：`menus` 为**嵌套树**（目录 M → 菜单 C → 按钮 F，逐级通过 `children` 挂载），根节点 `parentId=0`；`type` 取值 `M`/`C`/`F`；子节点 `path` 可为相对路径（如 `policy`），前端统一归一化为 `/icp/policy`。非目录节点无 `children` 字段。仅返回角色已授权的节点及其**祖先节点**（不会出现子菜单挂在根级）。

登录失败：40101（密码错）/ 40102（锁定，`data` 可带剩余秒数）；连续 5 次失败锁 15 分钟（`sys_config` 可配）。

风险评分规则：`risk_score = probability × impact`；高 ≥15、中 8–14、低 ≤7（`sys_config` 可配阈值，M2 起生效）。

M2b 实现口径（Lead 冻结，2026-11-03）：

1. **审批过渡**：M2b 阶段 `POST /policies/{id}/submit`、`POST /evaluations/{id}/submit` 只做状态流转（0→1）并返回 `data.pendingWorkflow=true`，`flow_instance_id` 置空；M2c 接入 Flowable 后改为真实发起流程（响应增加 `processInstanceId`），本口径在 docs/07-M2b 记录为过渡偏差。
2. **导出**：后端不提供导出接口，制度/风险/缺陷的导出由前端 `src/utils/exportCsv.ts` 用列表接口（pageSize 上限 500）生成 CSV（UTF-8 BOM）；后端仍需对列表做数据权限与按钮权限校验。
3. **风险阈值配置项**：实际读取 `sys_config` 的 `icp.risk.highScore`（默认 15）、`icp.risk.midScore`（默认 8）；种子未写入这两个 key，取不到用默认值；`sys.risk.thresholdHigh/Medium` 作废（记 docs/07 偏差）。
4. **矩阵覆盖率口径**：`covered` = 至少关联 1 个控制点的风险数；`rate = covered / total`（保留 2 位小数，实际实现为 1 位小数 `coverageRate`，见第 8 条）；按等级分组由前端基于 `items[].riskLevel` 聚合。
5. **评价计划启动生成任务**：以矩阵行（risk+control，coverage≥1）为模板，`evaluate_dept_id` 取风险责任部门、`evaluator_id` 取入参或当前用户；同一计划重复 start 不重复生成（幂等），返回已生成任务数。
6. **缺陷详情 `rectifyId`**：`icp_defect` 表无 `rectify_id` 列，接口返回的 `rectifyId` 为按 `defect_id` 反查最新整改单的瞬时字段；缺陷关闭条件为 `status=2` 且存在 `status=2`（已通过）的整改记录。
7. **时间格式**：`LocalDate` → `yyyy-MM-dd`，`LocalDateTime` → `yyyy-MM-dd HH:mm:ss`（JacksonConfig 全局序列化）；ID 仍以 JSON number 返回，前端按字符串处理。
8. **矩阵覆盖率响应形状（M2b 实际实现）**：`GET /matrices/coverage` 返回 `{totalRisks, coveredRisks, uncoveredRisks, coverageRate, items:[{riskId, riskCode, riskName, riskLevel, controlCount, covered}]}`；`coverageRate` 保留 1 位小数（如 100.0），`items` 覆盖全部风险。前端按此取值，`byLevel` 由前端按 `riskLevel` 聚合（原 docs/01 B16 的 total/covered/rate/byLevel 形状作废，记录于 docs/07-M2b 偏差）。
9. **整改提交证据 `evidence`**：`POST /rectifies/{id}/submit` 的 `evidence` 为 **String**（逗号分隔附件 id，如 `"4001,4002"`，落 `icp_rectify.evidence VARCHAR`），不是数组；前端在 api 层 `join(',')`。记录于 docs/07 偏差。
10. **矩阵唯一键现状**：`icp_matrix` 为 `UNIQUE KEY uk_risk_control (risk_id, control_id)`（不含 deleted 条件），逻辑删除后同一组合再次创建会命中 DB 唯一键返回 40002；M2b 未改动，作为已知限制记 docs/07（后续可用「恢复原行」语义处理）。

### 5.1 M2c 实现口径（Lead 冻结，D30–D34）

1. **引擎与建表**：真实 Flowable 7（`flowable-spring-boot-starter-process`）内嵌 Spring Boot 3.3.4，共用项目实例 `127.0.0.1:3307/icp_platform`；`ACT_*` 表由 Flowable 自动创建（`flowable.database-schema-update=true`），**不入 Flyway**；Flyway 只负责 `wf_form/wf_process_meta/wf_business_link/wf_task_urge/wf_purchase/wf_seal` 等业务表。`flowable.history-level=full` 以保证历史与留痕。
2. **BPMN 部署**：6 个 `backend/src/main/resources/processes/{key}.bpmn20.xml`，应用启动时自动部署（deployment name=`icp-processes`）；同 key 新部署形成新版本，`wf_process_meta.version` 同步最新版本号。
3. **办理人规则**：节点用 `candidateGroups`（`ADMIN` / `ICP_MANAGER` / `DEPT_MANAGER` / `MANAGEMENT`）表达候选角色，发起节点 `assignee=${initiator}`；`GET /workflow/todo` 返回候选组命中当前用户角色 ∪ assignee=当前用户的运行任务。加签/委派/转办留二期。
4. **表单**：实例启动时把 `formData` 以 JSON 写入流程变量 `formData` 并同步落业务表；`GET /tasks/{taskId}` 返回 `formSchema`（来自 `wf_form`）与 `formData`；`approve` 可带 `formData` 覆盖变量（只读节点忽略）。表单校验由后端业务校验 + 前端 schema 双重保证。
5. **驳回语义**：`POST /tasks/{id}/reject` 统一跳回发起节点（Demo 语义），实例 `status=REJECTED`，业务单据状态回退（政策/评价/采购/用印→草稿 0，整改→0，借阅→关闭）；发起人可对同实例重新提交（`POST /instances/{id}/resubmit`，M2c 新增），重提后回到首个审批节点并留历史。
6. **催办**：`POST /tasks/{id}/urge` 落 `wf_task_urge`（task_id/urge_user/urge_time/content）+ 生成 `coll_message`（type=URGE）；不改变流程状态；同一任务允许重复催办。
7. **超时**：配置 `workflow.timeout.hours=48`（`sys_config`，默认 48）；`GET /workflow/monitor` 对运行中实例按 `startTime + timeout` 计算 `overdue=true`；定时扫描由 M2e 接入（本阶段仅查询时计算）。
8. **抄送**：M2c 以站内信落地（`coll_message` type=CC），不做独立抄送列表页；消息中心在 M2d 展示。
9. **历史留痕**：`GET /instances/{id}/history` 来自 `ACT_HI_ACTINST` + `ACT_HI_TASKINST` + `ACT_HI_COMMENT`（审批意见），字段 `activityId/nodeName/assignee/action(审批|驳回|发起|重提)/comment/startTime/endTime`；`GET /instances/{id}/diagram-highlight` 返回 `{activityId, finishedActivityIds}`，前端 bpmn-js 只读高亮。
10. **M2b 过渡消除**：`POST /policies/{id}/submit`、`POST /evaluations/{id}/submit` 改为**真实发起流程**（D34），返回 `{pendingWorkflow:false, processInstanceId, taskId, businessNo}`；审批通过后由流程回调把单据推进到下一状态（制度→生效、评价计划→执行中），不再由前端二次改状态。`pendingWorkflow` 字段保留以兼容旧响应。
11. **seed 运行数据**：`scripts/seed-flow.ps1` 通过 REST 发起（不直写 `ACT_*`），实测目标：**60 个实例（40 运行中 / 20 已完成）**、40 条待办、20 条催办、意见与附件若干；可重复执行（先 `db-reset` 且应用已启动），重复执行为 SKIP（幂等，数量不翻倍），失败即退出非 0。运行中取 40 是为了同时满足「40 待办 + 20 催办」的目标（原「约 30/30」为估算值，M2c 按实测修正）。
12. **流程监控**：`GET /workflow/monitor` 查询参数 `status(running|completed|rejected)/overdue/processKey/keyword/timeoutHours`；返回 `wf_business_link`+实例节点的联表视图（不直接暴露 ACT_* 字段名）；`timeoutHours` 仅验收覆盖用（C15），默认取 `sys_config.workflow.timeout.hours=48`。
13. **resubmit 参数**：`POST /instances/{id}/resubmit?comment=...`（query 参数，Content-Type 任意），重提后实例回到首个审批节点，历史保留原驳回记录。
14. **独立单据接口**：采购 `GET/POST /purchase`、`GET /purchase/{id}`、`POST /purchase/{id}/submit`；用印 `GET/POST /seal`、`GET /seal/{id}`、`POST /seal/{id}/submit`；借阅 `GET/POST /borrows`、`GET /borrows/{id}`（借阅通过后联动 `coll_doc_borrow.status=1`）。均支持 `POST /instances` 带 `businessType` 直接发起。

### 6.1 M2d 实现口径（Lead 冻结，D36–D38）

1. **任务状态机**：`coll_task.status` 0 待处理 → 1 进行中 → 2 已完成 / 3 已取消；逾期由 `plan_end < now && status in (0,1)` 查询期计算（不落库，列表返回 `overdue=true`）。`POST /tasks/{id}/start` 仅 0→1；`complete` 仅 0/1→2；`cancel` 仅 0/1→3。子任务（`parent_id` 非空）独立流转，父任务完成不联动子任务、子任务完成不自动完成父任务（前端提示）。
2. **任务权限与数据范围**：`collab:task:list/get/add/edit/delete/complete/cancel/export/comment/remind`。数据范围：ADMIN/审计/管理层按 `@DataScope`（本部门/下级等）；普通员工仅「我负责(`assignee_id`) 或 我创建(`creator_id`)」；`GET /tasks/my` 固定按当前用户过滤。删除仅创建人或 ADMIN（逻辑删除）。
3. **截止提醒**：`POST /tasks/{id}/remind`（权限 `collab:task:remind`）落 `coll_message`，`message_type=3`（任务）+ `biz_type='REMIND'` 给负责人；定时扫描（M2e）统一按 `remind_time` 与 `plan_end` 生成提醒，M2d 只提供手动接口与前端到期高亮。
4. **文档状态机**：`coll_doc.status` 0 草稿 → 1 已发布 → 2 已归档；`publish` 0→1、`archive` 1→2；`GET /docs` 对无权限用户只返回其可见文档（见第 5 条）。`version` 为 `V主.次` 字符串，`PUT /docs/{id}` 内容变更时次版本 +1（V1.0→V1.1，V1.9→V1.10，主版本不动；不保存历史版本文件；历史版本二期）。
5. **文档权限模型（D37，以实际 DDL 为准）**：`coll_doc_perm(doc_id, target_type, target_id, perm_type)`——`target_type` 0 全员 / 1 角色 / 2 用户 / 3 部门（全员用 `target_type=0,target_id=0` 约定，种子无此值但 API 允许）；`perm_type` 1 查看 / 2 下载 / 3 编辑（可多行组合）。接口按原始三元组暴露，`PUT /docs/{id}/perms` 全量覆盖=物理删除旧行后插入（唯一键不含 deleted）。下载/详情校验顺序：已发布 → 命中下载或编辑权限 → 未命中但有该文档「已通过」的借阅单（`coll_doc_borrow.status=1`）→ 允许；否则 40300。`DELETE /docs/{id}` 仅草稿或 ADMIN（逻辑删除）。
6. **借阅联动（D33/D38）**：`coll_doc_borrow.status` 0 申请中 / 1 已通过 / 2 已驳回 / 3 已归还（以 DDL 与 M2c 回调为准）。`POST /borrows` 建单并发起 `doc_borrow` 流程（复用 D34 口径）；审批通过回调置 1、驳回置 2；`POST /borrows/{id}/return` 1→3（经办人/ADMIN）；下载兜底判 status=1。`GET /borrows` 普通用户仅本人申请。
7. **公告**：`coll_notice.status` 0 草稿 → 1 已发布 → 2 已关闭。范围以实际列 `coll_notice.dept_scope`（VARCHAR）编码：`全公司`=scope1 / `DEPT:2,3`=scope2 / `ROLE:EMPLOYEE,AUDITOR`=scope3；API 返回解析后的 `scope` + `scopeDeptIds`/`scopeRoles`，`PUT` 接受 `scope`+ids 反写该列；新公告默认 scope1。`GET /notices` 仅返回发布中且命中范围的公告；`POST /notices/{id}/read` 幂等写 `coll_notice_read`；`unread-count` 为用户维度未读数。
8. **消息与 SSE（D36）**：`GET /messages/stream?access_token=<JWT>`（EventSource 不能自定义 header，服务端从 query 读取并校验，日志对 token 脱敏）；事件名 `message`，data 为 `{id,type,title,content,createTime}`；心跳 30s（`: ping`）；单用户最多 3 条连接，超限关闭最旧；断线由前端指数退避重连（1s/2s/4s… 上限 30s）。`POST /messages/read` 批量置已读；`POST /messages` 仅 ADMIN（系统消息）。
9. **日程**：`coll_schedule.status` 0 待开始 / 1 进行中 / 2 已结束 / 3 已取消；类型 1 会议 / 2 提醒 / 3 个人日程。`GET /schedules/calendar?month=yyyy-MM` 返回 `{items:[{id,title,start,end,type,status}]}`；`POST /schedules/{id}/cancel` 置 status=**3**（2 只表示时间已结束，由时间推导或收尾任务更新）；结束时间必须晚于开始时间（否则 40000）；跨部门会议对参与部门可见。
10. **数据权限映射（D38）**：`coll_task.assignee_id/creator_id/dept_id`、`coll_doc.dept_id/owner_id`、`coll_notice.dept_id/role_code`、`coll_schedule.owner_id/dept_id`、`coll_message.user_id`；统一走 `@DataScope` 与本人维度，越权详情 40300。
11. **菜单与按钮**：沿用 `coll/task`、`coll/doc`、`coll/doc-borrow`、`coll/notice`、`coll/schedule`、`coll/message` 路径（已存在，M2d 全部可见）；按钮权限按 docs/05 矩阵补齐，`collab:doc:preview` 暂缓（M2d 只下载）。
12. **不做（M2d 范围外）**：在线文档预览/编辑、文档历史版本下载、任务甘特图、会议纪要生成、邮件通知、消息推送（App/短信）。

### 7.1 M2e 实现口径（Lead 冻结，D39–D41）

1. 数据来源：全部实时 SQL 聚合业务表（`icp_*`/`wf_*`/`coll_*`/`sys_*`），不建汇总表、不写历史快照；仅 `GET /dashboard/summary` 允许 Caffeine 60s 缓存（key 含 userId 与数据范围）。
2. 返回形状（均位于统一 `data` 内）：
   - `GET /dashboard/summary` → `{policies:{total,effective}, risks:{total,high}, coverage:{totalRisks,coveredRisks,coverageRate}, defects:{total,unclosed}, rectify:{total,approved,rate}, workflow:{todo,overdue}, tasks:{overdue}, messages:{unread}}`
   - `GET /dashboard/trend?months=6`（1–12，默认 6）→ `{labels:[yyyy-MM], newPolicies:[], newDefects:[], rectifyClosed:[], avgProcessHours:[]}`
   - `GET /reports/icp-coverage?deptId=&year=` → `{totalRisks, coveredRisks, coverageRate, byDept:[{deptId,deptName,total,covered,rate}], byCategory:[{categoryId,categoryName,total,covered,rate}]}`
   - `GET /reports/risk-distribution?dim=level|category|dept` → `{dim, items:[{name,value}], total}`
   - `GET /reports/rectify-rate?year=&deptId=` → `{total, approved, rate, byDept:[{deptId,deptName,total,approved,rate}], byMonth:[{month,total,approved,rate}]}`
   - `GET /reports/process-duration?processKey=&months=6` → `{items:[{processKey,processName,total,avgHours,p95Hours}], byMonth:[{month,avgHours,count}]}`
   - `GET /reports/defects?severity=&status=` → `{items:[{severity,status,count}], total}`
   - `GET /alerts?type=&pageNum=&pageSize=` → 分页 `{list:[{id,type,level,title,bizType,bizId,dueTime,daysLeft?,overdueDays?}], total, pageNum, pageSize}`；`type` ∈ `task_overdue` / `policy_expiring` / `defect_high_risk` / `process_overdue`
   - `GET /alerts/count` → `{taskOverdue, policyExpiring, defectHighRisk, processOverdue, total}`
3. 统计口径：`coverageRate = coveredRisks/totalRisks`（covered = 风险至少有 1 条 **status=1 生效** 的控制矩阵）；`rectify.rate` = 整改 status=2 已通过 / 总数；**高风险 = `icp_risk.risk_level=1`（字典 1=高/2=中/3=低）**；预警四类：任务逾期（`coll_task.plan_end < 今天` 且 status∈(0,1)）、制度到期（生效中且 `expire_date` 在 [今天, 今天+30 天]）、高风险缺陷（`icp_defect.severity=1` 重大 且 status≠3 已关闭；字典 1=重大/2=一般/3=轻微）、流程超时（运行中实例开始时间 + `workflow.timeout.hours`(48h) < 现在）。
4. 权限：沿用既有菜单权限串，不新增菜单/按钮、不改种子——`report:icp:view`、`report:risk:view`、`report:rectify:view`、`report:process:view`、`report:alert:view`；工作台 `GET /dashboard/summary|trend` 用 `hasAnyAuthority('report:dashboard:view','dashboard:workbench:view','dashboard:todo:view')`（EMPLOYEE 有工作台菜单 61/62 但无 `report:*`）。
5. 数据范围（D41）：报表与预警列表统一 `@DataScope` 按部门过滤（制度/风险按 `owner_dept_id`，缺陷/整改按 `dept_id`，任务按 `assignee_id`/`dept_id`，流程按发起人部门，公告/日程按各自范围）；ADMIN/ICP_MANAGER/AUDITOR/MANAGEMENT 全部，DEPT_MANAGER 本部门及下级，EMPLOYEE 本人相关。
6. 定时扫描（D40）：进程内 `@Scheduled(fixedDelay=600000)`（每 10 分钟、initialDelay 60s、开关 `report.scheduler.enabled`）读取 `sys_job(status=1)`，**不解析 cronExpression**（按 status=1 全量执行，记偏差），按 `job_name` 映射 5 个 handler：制度到期扫描 / 评价任务逾期扫描 / 任务到期提醒 / 缺陷整改超期提醒 / 公告定时发布；命中后写 `coll_message(message_type=3)` 并落 `sys_oper_log`（`title=定时任务-<jobName>`；该表无 module 列，按 title 过滤）；同一 `(receiver_id,biz_type,biz_id,当天)` 去重；`POST /jobs/{id}/run` 手动触发复用同一 handler（M2a 接口语义升级为真实执行）。
7. 前端：工作台 `dashboard/index` 接 summary+trend，`report/*` 5 页接对应接口 + ECharts（空数据展示空态、加载骨架、错误重试）；预警中心支持类型筛选与跳转业务详情。
